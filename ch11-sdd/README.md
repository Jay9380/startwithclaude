# 11장 · 스펙 주도 개발(SDD) — 체크박스 스펙은 6/6, 스펙 드리프트는 규칙 한 줄이 막는다

책 11장은 같은 프롬프트("로그인 만들어 줘")가 매번 다른 결과를 내는 문제에서 출발한다. 스펙을 **실행 가능한 계약**으로 저장소에 두라는 것이 해법이다.
스펙의 세 요소는 Context(어디서), Control(무엇을 만들고 무엇은 만들지 않을지), Correctness(완료를 어떻게 증명할지)다.
책은 GSD Redux로 `til-cli`(오늘 배운 한 줄을 날짜별 마크다운에 누적)를 만든다.

**GSD는 설치하지 않았다.** `npx @opengsd/get-shit-done-redux`가 전역 `~/.claude`에 명령어를 등록하기 때문이다(공유 PC의 다른 세션에 영향).
대신 같은 `til` 과제로 책의 주장 두 가지를 쟀다.

```bash
cd ch11-sdd/experiments
./spec_lab.sh 3        # A. 한 줄 요청 vs 체크박스 스펙 vs 산문 스펙 (haiku, 숨은 수용 테스트 acceptance.py)
TAG=b ./spec_lab.sh 3 "checkbox prose"   # 3회 더
./drift.sh 3           # B. 새 세션의 기능 추가와 스펙 드리프트 (haiku 9회)
```

## A. 같은 과제, 세 가지 입력 (`spec_lab.sh`, `specs/`, `acceptance.py`)

**한 줄 요청**(책의 `/gsd-new-project` 프롬프트와 같은 문장)을 3번 보냈다. 끝나면 정한 것을 보고하게 했다.

| 회차 | 언어 | 저장 경로 | 줄 형식 |
|---|---|---|---|
| 1 | JavaScript | `현재디렉토리/TIL.md` (파일 하나) | `# YYYY-MM-DD` 아래 `- 내용` |
| 2 | Node.js | `~/.til.md` | `## YYYY-MM-DD` 아래 `- 텍스트` |
| 3 | JavaScript | `./til/YYYY-MM-DD.md` | `- HH:MM:SS message` |

세 번 모두 저장 경로와 형식이 달랐다. 책 그림 11-1(JWT / Passport / NextAuth)과 같은 현상이다. 셋 다 "맞는" 구현이지만 서로 호환되지 않는다.

**스펙 두 가지**는 내용이 같고 쓰는 방식만 다르다.
- `til-checkbox.md`는 C-C-C 구조에 수용 기준을 체크박스 5개로 적었다.
- `til-prose.md`는 같은 요구를 산문 한 문단으로 적었다.

채점은 모델에게 보여 주지 않은 `acceptance.py`의 7개 항목으로 했다. 항목은 형식, 같은 날 누적, 빈 입력 거부, UTF-8, 로컬 시간대, 동시 실행 20개, 기본 경로 `~/til`이다. 로컬 시간대 검사는 TZ를 UTC+14와 UTC−11로 바꿔 돌린다. 기본 경로 검사는 HOME을 임시 폴더로 바꿔 돌린다.

| 스펙 | 7/7 만점 | 비고 |
|---|---|---|
| 체크박스 (C-C-C) | **6/6** | |
| 산문 한 문단 | 5/6 | 1회는 **실행조차 안 됨**: `open(path, "a")` 뒤 `f.read()` → `UnsupportedOperation`. 그 회차는 3턴(작성→보고)으로 끝났고 한 번도 실행해 보지 않았다 |

- 책(11.4.2)은 "수용 기준은 반드시 체크박스로, 산문으로 쓴 제약보다 훨씬 잘 지켜진다"고 했다. 방향은 같지만 차이는 6회 중 1회로 작다. haiku도 산문 요구를 대부분 지켰다.
- 더 큰 차이는 한 줄 요청과 스펙 사이에 있다. 결정이 고정되느냐 매번 바뀌느냐의 차이다. 그리고 **스펙이 있어야 채점 자체가 가능하다**. 한 줄 요청의 결과물에는 돌릴 수 있는 공통 테스트가 없다.

## B. 스펙 드리프트 (`drift.sh`)

A의 체크박스 스펙으로 만든 `til.py`(7/7)와 `specs/til.md`가 있는 저장소에서 새 세션에 요청했다. 요청은 "til.py에 --tag 옵션을 추가해 줘"다.
스펙의 **Out of Scope에 '태그'가 있다**. 올바른 처리는 둘이다. 충돌을 짚거나, 기능을 넣는다면 같은 변경에서 스펙도 고쳐야 한다(책 11.4.2 "스펙 드리프트").

| CLAUDE.md | 스펙 읽음 | 보고에 스펙 언급 | 스펙 갱신 | `--tag` 동작 |
|---|---|---|---|---|
| 없음 | 0/3 | 0/3 | 0/3 | 3/3 |
| 책 11.4.4의 한 줄 ("코드 작업 전에 specs/의 관련 스펙을 먼저 읽고…") | 2/3 | **0/3** | **0/3** | 3/3 |
| 위 + "코드 동작을 바꾸면 같은 변경 안에서 스펙도 함께 갱신" | 2/3 | 2/3 | **2/3** | 3/3 |

- 스펙이 없는 저장소처럼 행동했다(1행). 코드는 동작하지만 스펙은 "태그는 범위 밖"이라고 말하는 채로 남는다. 바로 스펙 드리프트다.
- 책의 한 줄(2행)은 스펙을 **읽게** 만들었다. 하지만 읽고도 Out of Scope 충돌을 말하지 않았고 스펙을 고치지 않았다. **읽기와 갱신은 별개의 지시**다.
- 갱신 규칙을 한 줄 더하자(3행) 2/3이 스펙을 함께 고쳤다. Out of Scope에서 '태그'를 지우고 Control과 수용 기준에 태그를 추가했다. 그래도 1/3은 여전히 스펙을 열지도 않았다. 확실히 하려면 PR 체크(코드 변경에 스펙 변경이 없으면 경고)처럼 장치로 옮겨야 한다.

## 하지 않은 것

- GSD·OpenSpec·Spec Kit 설치: 모두 전역 또는 프로젝트의 `.claude/`에 명령어·스킬을 생성한다. 책의 GSD 흐름(4-에이전트 리서치 → PROJECT/REQUIREMENTS/ROADMAP/STATE → plan-checker)은 노트에서 정리했다.
- 우로보로스(Ambiguity 점수): 플러그인 설치가 필요하다.
